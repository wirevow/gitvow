# Changelog

## 0.28.3 — 2026-09-22
- **An install refreshes an untouched copy of the default policy.** `install` copied the default policy once and never again, so a repository kept the rules of the version it was installed with: none of today's rule changes (the git rules as program rules, targets, the indirect tier) reached the founder's own repositories, and a stale `\bgit\s+push\b` pattern stopped an MCP verification that merely mentioned a push in a JSON string. The copy now carries `_from_default`, the digest of its own body; an install that finds the body still equal to the marker replaces the file with the current default and says so. A copy a person edited is left alone and named; a copy from before the marker existed is left alone and named, with `gitvow policy` to compare. If you keep the default, delete the marker-less copy and rerun `gitvow install` once to get a stamped one.
- **`kubectl exec` is its own class.** `exec`, `port-forward`, `cp` and `debug` were verbs of "cluster mutation"; they are not mutations, they are a person's hands inside a running workload, and the text of the command cannot tell a read from a write. They now ask as "exec into a production workload" for `prod|live` contexts and are observed elsewhere, so standing for reading through exec never becomes precedent for applying manifests. Found when a teammate's agent was asked about a read-only query run through exec, and the question was right but the label was wrong.

## 0.28.2 — 2026-09-22
- **The git rules are program rules now, so `git -C <dir> push` is a push.** The default policy's three git rules were `pattern` rules that needed `git` and its verb adjacent; every push made through `git -C <repository> push` walked past them, which a day of dogfooding produced dozens of times before the hook log showed it. Same bug class the kubectl rules had until 0.17.1, now closed the same way: `{"program": "git", "verbs": [...]}`, which admits `-C dir`, `-c k=v` and any other option between the two. Force pushes and history rewrites deny as before, through any such option.
- **Pushes ask for protected branches and are observed elsewhere.** With `target` from 0.27, the push rule asks immediately when the destination branch is `main`, `master`, `production` or `release*` (or cannot be read), and observes every other push: the record shows them, nobody is interrupted for a feature branch.

## 0.28.1 — 2026-09-22
- **The pending-commit window is policy, and a commit that lands past it is said out loud.** The git hooks treated the agent's commit as the agent's for five minutes after the gate saw the `git commit` command; a harness that runs tool calls in parallel can queue that command behind a long test run, and our own 0.28.0 release commit landed seven minutes later with no trailer and no note, silently. The window is now `decisions.commit_window_seconds` (default 1800), written into the session state by the gate so the hooks read it without loading policy; a state written by an older gitvow keeps the original five minutes. When a commit still lands past the window, `PostToolUse` measures the gap, logs `commit_without_trailer`, and tells the agent which commit carries no record and why. Re-run `gitvow install` in each repository to refresh the hook bodies.

## 0.28.0 — 2026-09-22
- **The record server: any agent asks the record, read-only.** `gitvow serve` speaks MCP over stdio and exposes one repository's record as tools: `record_brief`, `record_claims`, `record_standing`, `record_why`, `record_recall`, `record_handoff`, `record_pack`, `record_check` (a dry run of the policy) and `record_status`. `gitvow serve --print-config` prints the registration for Claude Code, Cursor and Codex. Nothing writes through it: no state, no log line, no note, no network; it is only reachable over the stdin and stdout of the agent that started it.
- **Coverage on every answer.** Each result carries how many decisions, claims and session notes exist, where the brief came from and how old it is, whether the pack applied, and a level (`full`, `partial`, `none`); a consumer treats `partial` and `none` as absent, never as a clean bill. **Quoted content is data:** claims and stated plans are rendered inside a block that says so, and carried as structured fields, never as prose an agent could read as its instructions.

## 0.27.0 — 2026-09-22
- **Rules on what a command reaches, not only on what it says.** A `{program, verbs}` rule may add `target`, a regex on the command's reach, read from the environment before it runs and only once the rule has matched: for `kubectl` and `helm` the context from `--context`/`--kube-context` or the kubeconfig's `current-context`, plus the namespace; for `git push` the remote URL and the branch; for `terraform` the workspace under `-chdir`. The default policy now asks immediately for a cluster mutation or a helm release change whose context matches `prod|live`, and **observes** the same commands elsewhere: the record grows, nobody is interrupted for a kind cluster. A target that cannot be read matches every target rule, so an action of unknown reach is asked about, never waved through. The target is part of the finding's subject (`run kubectl (cluster mutation in production) @ context=prod-in`), so standing accrues per place reached: three answers for staging say nothing about production.
- **Commands the gate cannot read are recorded instead of passing.** `eval`, `source`, a variable in program position (`$KUBECTL delete`) and a shell running a script file (`bash deploy.sh`) used to fall through to allow. They are now a tier of their own, `decisions.indirect_commands`, `observe` by default (recorded on the commit, nobody asked), settable to `commit`, `immediate` or `allow`. The record shows how often it happens before anyone decides whether it deserves a question.
- `gitvow check` and the card show the resolved target beside the command. Policy validation rejects `target` on `pattern` rules (it has nothing to attach to) and bad target regexes.

## 0.26.1 — 2026-09-22
- **`{program, verbs}` rules match the program in command position.** A rule written as `{"program": "kubectl", "verbs": ["exec", …]}` fired wherever the two words appeared on the line, so `gh issue create --body "how to size: kubectl exec into the pod"` was a cluster mutation and a commit message that quoted `terraform apply` was an infrastructure change. Reported the day 0.26.0 shipped, by an agent writing an issue whose body described a runbook. The line is now split into its simple commands (`;`, `&&`, `||`, `|`, newlines), heredoc bodies are dropped, assignments and `sudo`/`env`/`time`/`timeout N`/`nohup`/`xargs` are stepped over, and a `sh -c "…"` argument is read as a command line of its own; the program must be the word that runs. `kubectl --context prod delete`, `sudo kubectl delete`, `bash -c 'kubectl delete'` and `… | xargs kubectl delete` still deny; a mention inside another program's argument does not. A line that cannot be tokenised falls back to the whole-line regex, failing toward asking. `pattern` rules are unchanged and documented as such.

## 0.26.0 — 2026-09-22
- **A page that says exactly what gitvow touches.** [`docs/trust.md`](docs/trust.md): what is read, written, executed and sent, scoped to be checked against the code, with the reversals this tool has made and why. The security page keeps the bypass surface; this one is what a reviewer reads first.
- **Credential-store paths are excluded by path, everywhere gitvow stores content.** `.env*`, `.npmrc`, `.netrc`, `.pgpass`, `.git-credentials`, `.kube/config`, `.aws/credentials`, SSH private keys, `credentials.*`, `secrets.*`, key material by suffix, and configuration files under `secrets/` or `credentials/` directories: never snapshotted, never kept as an attribution blob (`blob_skipped` in the hook log). The list is loaded after the policy's own `snapshots.exclude`, which now adds to it and can no longer replace it. Classification is by path, never by content; redaction on values is unchanged and still best effort.
- **Every write into a repository is preflighted, and skipped when unchanged.** `install`, `rules` and `claims` refuse a target that resolves outside the repository, into its git directory, onto a non-regular file or onto a hard link, by name, and write nothing; a checked-in symlink at `.claude/settings.json` cannot redirect them. Bytes already current are not rewritten, so a rerun no longer moves the hook mtime that `status` uses as the install stamp, which had been hiding ungated commits made before a rerun.
- **`gitvow status --line`**: one line for an agent's status bar from the repository's session state and hook log: `[gitvow 0.26.0] 2 decided · 5 recorded · 1 open · 3 asked · 0 denied`. A repository with no session says so.
- Caches: documented that the pack and brief caches are copies of what a store published and derive from neither the policy nor the version, so nothing needs invalidating when a policy changes.

## 0.25.0 — 2026-09-22
- **The record lives in the repository the change is about.** Until now every hook resolved the repository from the session's working directory, so a session opened in one checkout that edited a file in another, or ran `git -C ../other commit` or `cd other && git commit`, was gated by the wrong policy, wrote its findings into the wrong `.git`, and left the other repository's commits with no trailer and no note. The replay of three engineers' sessions had already found 28% of edits landing outside the session's own checkout; our own repositories carried zero decisions for the same reason. `PreToolUse` and `PostToolUse` now resolve the target repository from the tool call itself: the edited file's checkout for `Edit`/`Write`/`MultiEdit`/`NotebookEdit`, the `git -C <path>` or leading `cd <path> &&` of a Bash command. That repository's policy is the one evaluated, its state holds the findings and the pending-commit flag, its commit gets the trailers and its notes ref gets the note. Anything outside every repository still falls back to the session's own checkout, as before.
- The session's own state keeps `repos_touched`, and the ledger entry written at Stop lists them, so a session that reached three repositories says so in one place.

## 0.24.0 — 2026-09-17
- **The `http` sink: a store over the network.** Until now a sink was a local path, which works for one platform team with a shared clone and not for thirty laptops. `{"name": "acme", "type": "http", "url": "https://store.acme.internal", "token_env": "WIREVOW_STORE_TOKEN"}` points the collector at a store that speaks the store protocol's verbs: `POST /v1/bundles` to begin (idempotent by digest, the server says which parts it already holds), `PUT /v1/bundles/{digest}/parts/{path}` for each part, `POST /v1/bundles/{digest}/commit` with the attestation. The server verifies every part's sha256 before anything is written. The pack and the brief come back from the same server (`GET /v1/rules`, `GET /v1/brief`). The bearer token comes from the environment variable `token_env` names, or from `token` in the local sink file; never from a committed file, like every other sink setting. TLS is the customer's proxy's job.
- **A refusal is not queued.** A 4xx from the store (wrong token, a bundle the store refuses) is reported with the server's reason and the bundle is not put in the outbox, because retrying a refusal changes nothing. Unreachable (no connection, timeout, 5xx) queues as before and drains on the next sync. Sinks needing a `url` and sinks needing a `path` are validated when read.
- The server side is `wirevow store serve` in the private store package: the same store the platform team already runs, reachable over HTTP. It is not a hosted store.

## 0.23.0 — 2026-09-17
- **The organisation pack: rules pushed down, applied as a layer that tightens and never loosens.** A store publishes `packs/<source>.json` per repository: `bash_deny`, `bash_confirm` and `path_confirm` rules a named person accepted for the organisation, optional `settings.decisions`, and a mandatory `expires`. `gitvow sync` copies it from a `git` sink to `~/.gitvow/cache/packs/<source>.json`; `load_policy` applies it under the repository's own policy. Pack rules are added and tagged with the pack they came from; a pattern the repository already has is not added twice, so the repository's own tier stands. Pack settings may set `mode` to strict, turn `session_scope` off or raise `rule_threshold`; they can never loosen any of them. A pack that is missing, expired or malformed changes nothing, and `gitvow pack` says why. The pack is never written into `.gitvow/policy.json`: `load_policy(pack=False)` is the repository's own policy and is what the policy writer uses.
- **The brief, from the cache.** The same sync fetches `brief/<source>.json`, the store's account of what the organisation's record says about this repository: standing per finding class with recall from other repositories, accepted rules, confirmed claims, gaps. Session start hands it to the agent with its age and `source: cache`, marks it stale past the store's `stale_after`, and says in every rendering that it is context, not permission. `gitvow brief` prints it for a person and falls back to the repository's own record as `source: repo` when nothing is cached. Nothing is fetched during a tool call, ever: the gate reads a file or nothing.
- `gitvow sync` reports what came back per sink (`from the store: pack fetched, brief unchanged`); a `dir` sink returns nothing, being a drop and not a store.

## 0.22.0 — 2026-09-17
- **`gitvow sync`: the collector.** Builds the export bundle and delivers it to every configured sink, or the one named with `--sink`. Two sink kinds, both run by the customer: `git`, a store repository in the store protocol's layout (the bundle lands under `bundles/<source>/<digest>/`, the source's frontier file is appended, one commit per bundle), and `dir`, a directory or mounted object-store prefix. Idempotent by digest: a bundle a sink already holds is reported, not resent. When a sink is unreachable the bundle waits in `~/.gitvow/outbox/<sink>/<source>/<digest>/` and the next sync drains the outbox oldest first before delivering the current record. `--dry-run` says where the bundle would go and moves nothing. The collector refuses to move anything but `kind: record`.
- **Sinks are never read from a committed file.** They live in `.gitvow/export.local.json` (which `gitvow install` now adds to `.git/info/exclude`) or `~/.gitvow/sinks.json`. A sink named in the committed `.gitvow/export.json` is ignored with a warning. A committed destination is how a contributor's record ends up in an upstream project's store; the shape is designed out rather than documented around. `gitvow sinks` lists what is configured and where it came from.

## 0.21.0 — 2026-09-17
- **`gitvow policy`: proposed policy rules, accepted as reviewed commits.** A batch loop outside this package replays the policy over recorded sessions and proposes rules for what the gate let through, each with its evidence (events, repositories, engineers, seen-at shapes) and its price in questions per engineer per week. `gitvow policy import <file>` accepts the loop's JSON output, a bare candidate list or a policy fragment, validates every rule's regex, redacts its reason, and queues it in `.git/gitvow-policy-proposals.json`. `gitvow policy` lists the queue, highest consequence first. `gitvow policy accept <n|id> [--when commit|observe|immediate]` appends the rule to `.gitvow/policy.json`, validates the resulting policy, and commits that file alone with `Gitvow-Policy-Accepted: <id> by <person> when=<tier>[: <reason>]` and the evidence in the message; when the repository has no policy file, the commit creates it from the shipped default first, so accepting never drops the defaults. `gitvow policy reject` writes `Gitvow-Policy-Rejected` on an empty commit; re-importing skips answered ids. Authority follows rule verdicts; staged work is refused. Two new trailer names; an older gitvow matches neither.

## 0.20.0 — 2026-09-16
- **`gitvow export`: the record leaves the machine as an inspectable directory, never the session.** One file per consented data class: `decisions.jsonl`, `claims.jsonl` (confirmed only), `observed.jsonl`, `rule-verdicts.jsonl` with the frozen evidence run, `meter.json`, and, only when the repository has consented, `sessions.jsonl` (counts, attribution, usage, edits-elsewhere counts; never the plan text or paths) and `gate-events.jsonl` (counts per session per reason; never a command). `manifest.json` carries the normalised remote, the frontier (head, note refs, window), the consent map, a sha256 per part and a digest over the whole, which is the idempotency key. `attestation.json` carries the redaction rules digest and every row refused. Consent lives in the committed `.gitvow/export.json`; `--consent a,b` overrides it for one run; a class not consented has no file and the manifest says so.
- **Redaction is re-verified, never applied.** Every string in every row runs through the repository's redaction rules at export; a row that would change is refused and listed in the attestation, because a rewritten row would mean the write-time edge failed and the failure was hidden.
- **Nothing sends.** This release produces the directory; sinks come with the store. `--dry-run --why` prints what would leave, what never does (transcripts, working trees, snapshots, command lines, prompts, person-reach claims) and what was refused.
- Canonical serialisation: rows sorted, keys sorted, no exporter-invented timestamps inside parts, so the same repository yields the same digest twice and a store can tell a resend from a change.
- `class` on decision rows is `null` in this version: not computed, never "no class"; the store derives it.

## 0.19.0 — 2026-09-16
- **`gitvow claims`: what the people who own the code said about it, confirmed by them, kept in git.** A claim is a statement in a person's own words with a source and a binding to paths. Candidates come from a batch job outside this package as a JSONL file (one object per line: `claim_id`, `text`, `speaker`, `kind`, `travels_with`, `paths`, `confidence`, `why`, `source`, `when`). `gitvow claims import <file>` queues the repo-reach ones in `.git/gitvow-claims.json` and appends person-reach preferences to the speaker's own `~/.gitvow/claims/preferences.jsonl`, which is never committed and never exported. `gitvow claims` lists the queue, most confident first. `gitvow claims confirm <n|id> [--paths] [--edit] [--reason] [--by]` and `gitvow claims reject <n|id> [--reason]` write an empty commit carrying `Gitvow-Claim-Confirmed: <id> by <person>[ paths=…][: <text>]` or `Gitvow-Claim-Rejected: <id> by <person>[: <reason>]`, plus a note on `refs/notes/gitvow/claims` (schema 1) with the text as recorded, the original verbatim text, `edited`, the paths, the speaker, the source pointer and the confirmer's standing (`speaker` when they said it themselves). A later rejection of a confirmed id withdraws it. Staged work is refused, as for rule verdicts.
- **Confirmed claims are context, never permission.** `gitvow claims --write` renders them into the agent's instruction file under a second managed section (`<!-- gitvow:claims -->`), attributed and dated, with the sentence that they permit nothing. Session start hands the agent the confirmed claims of the repository and, only for the person at the keyboard, their own preferences. `gitvow show` finds the claims note. The trailer grammar grows by two new names; an older gitvow matches neither.
- Redaction runs at import on every candidate's text, which is the write-time edge for this data class.
- Why now: the first knowledge-transfer engagement. The extraction that produces candidates runs outside this package, through Claude Code in print mode on the operator's own machine, and is not part of the open tool.

## 0.18.0 — 2026-09-16
- **`when: observe`, a third tier for a rule.** The finding is recorded on the commit as a new trailer, `Gitvow-Observed: <finding>`, counted by `gitvow digest`, `gitvow report` and the new `decisions.observed()` query, and nobody is ever asked about it. It is not on the card, it is not debt, and it can never become a rule. It exists because the alternative to a question is silence, and a pattern in observe leaves a count behind that says whether it deserves a question later. The card prints one line when observed findings are waiting ("Recorded, not asked: 2 observe-tier findings").
- **An immediate confirm is answered once per session.** Until now an immediate confirm (`git push`, `kubectl apply`) recorded nothing and was asked on every call; on Claude Code the agent could not even record a yes. It is now a numbered finding. The agent asks; `gitvow decide <n> accept --scope session` records the answer and the same question is not asked again until the session ends; the next commit carries it as `Gitvow-Accepted: run git (pushing to a remote) by <person> scope=session`, which is a scoped answer and therefore never precedent. `decide <n> decline` blocks the command for the session. On Cursor and Copilot the person's click on the agent's own approve button runs the command, and PostToolUse records that click as the session's answer (`approved at the agent's prompt`) so the record says what happened and the question is not repeated. A confirm nobody answered is not on the card and writes nothing to the commit, because the command never ran. `"decisions": {"session_scope": false}` asks every time and records nothing, as 0.17 did.
- **Why both, with a number.** Replaying 15,549 real tool calls from three engineers' sessions through the default policy priced the gate at 19.3 questions per engineer per week, 12.9 of them `git push`. A gate that asks that often is uninstalled. With session scope the push question is asked once per session that pushes; with observe the loop that proposes rules from what the gate let through can propose them at zero cost.
- **Edits outside the repository are counted and named.** The same replay found 28% of edits landing in a different checkout than the session's own. `_record_agent_blob` used to drop them. They are now counted per target repository in the session state (`edits_elsewhere`, with up to 20 relative paths each), the card names them ("Edits outside this repository: 2 in other-repo"), and the note carries them as `edits_outside_repository`. They are recorded in the session repository's note, not in the target's, and the card says so.
- Note schema 7: `decisions[].answer` may be `observed`; `edits_outside_repository` added. Additive. The trailer grammar grows by one new name, `Gitvow-Observed`; an older gitvow does not match it at all, which is the safe direction.
- **Re-run `gitvow install` in every repository after upgrading.** The `prepare-commit-msg` hook body changed (it writes `Gitvow-Observed` and skips unanswered immediate confirms) and so did `pre-commit` (observed and immediate findings never block a strict commit). `gitvow status` reports repositories still on the old body.
- Session state gains `session_answers` (answers to immediate confirms, kept until the session ends), `edits_elsewhere`, and the `immediate` and `observe` flags on findings. Hook log gains `observed`, `allowed_by_session_answer` and `prompt_approval_recorded` events.

## 0.17.1 — 2026-09-16
- **Fixed: an option between a program and its verb walked past every default command rule.** `kubectl --context prod delete pod x` was allowed, because the rule was `\bkubectl\s+(delete|drain|cordon)\b` and the verb had to be the word right after the program. The same held for `kubectl -n … apply`, `helm --kube-context … upgrade`, `terraform -chdir=… destroy` and `aws --profile … terminate-instances`. It was found by replaying 15,549 real tool calls from three engineers' sessions through the default policy: 163 cluster mutations, 49 of them deletes against production-named contexts, and not one was stopped. Nobody was bypassing anything. That is how people run kubectl, and the default policy was written for how examples run it. Same bug class as the `git -c … commit` form the commit gate mis-parsed until 0.16.
- Command rules may now be written as `{"program": "kubectl", "verbs": ["delete", "drain"]}` and gitvow builds the regex, allowing `--k=v`, `--k v` and bare flags between the two. `pattern` still works for shapes the form cannot express. The finding is `run <program> (<reason>)` either way. The default policy's kubectl, helm, terraform, pulumi and gh rules are rewritten in the new form; the aws rule keeps a pattern that allows options before and after the service name.
- The default confirm list grows by `kubectl create|replace|patch`, `helm rollback` and `gh secret set`, and by one new commit-time rule: **a direct write to a database** through a client on the command line (`mysql … -e "UPDATE …"`, `psql -c 'delete from …'`, and so on). The replay found 691 direct database sessions, mostly `SELECT`; the 39 `UPDATE`s, 52 `REPLACE INTO`s, 24 `CREATE`s and 8 `DELETE`s are the ones that now reach the card. `SELECT` and `grep UPDATE src/` stay free: the rule needs a client program and a writing statement on the same line.
- Reads are unchanged and tested as such: `kubectl --context prod get pods`, `aws --profile p s3 ls`, `helm template`, `SELECT`.
- Upgrading: no hook or schema change; `pip install -U gitvow` is enough. A repository whose own policy copied the old kubectl or helm patterns should rewrite them in the `program`/`verbs` form; `gitvow check -- kubectl --context x delete pod y` shows whether a policy has the hole.

## 0.17.0 — 2026-09-16
- **`decisions.mode` now governs the agent's commit, not only a person's.** Until now `open` and `strict` applied to a commit made from a terminal, while the card refused the agent's commit in both modes: advisory for people, blocking for agents, and nobody had chosen that split. In `open`, the default, the agent's commit is stopped once with the card; if the person answers, the answers go into the commit as before, and if they do not, running the commit again lets it through with a `Gitvow-Open` trailer for each unanswered finding. In `strict` the card refuses the commit until every finding is answered, exactly as before. Hard denies are unchanged in both modes.
- The open-mode card has its own header, `OPEN FINDINGS`, and says what happens on a second attempt. On Cursor and Copilot it is delivered as a question, so approving it is the answer "let it through" and the commit runs with the findings recorded as open; the strict card is still delivered as a refusal there, because a click on approve would run the commit with nothing recorded.
- Why: a gate that blocks by default gets uninstalled, and an uninstalled gate records nothing. "Nobody decided" is more useful as a count in `gitvow decisions` and the digest than as a wall in front of the commit. Strict is one line in the repository's policy for teams that want the wait, and an organisation rule pack, when there is one, will be able to set it and a repository will be able to tighten but never loosen it.
- Session state gains `card_ack`, the findings the open card was shown for; the hook log gains `card_ack` events and a `mode` field on `card` events. `gitvow selftest` checks the card under the shipped default. No trailer, note or policy schema changes; an existing `strict` policy behaves exactly as it did.
- **Behaviour change to know about before upgrading:** a repository running the default policy will see the agent's commit go through on its second attempt where 0.16 refused it indefinitely. If that repository wanted the refusal, add `"decisions": {"mode": "strict"}` to `.gitvow/policy.json`.

## 0.16.1 — 2026-09-15
- **`user_turns` counted the harness as a person.** The filter for text the agent writes into the user's own turn accepted only `[a-z_]` inside a tag, and every wrapper Claude Code uses is hyphenated — `<local-command-caveat>`, `<task-notification>`, `<system-reminder>`, `<command-name>` — so all of them were counted as something a human typed. The summary a session writes when it resumes after running out of context is plain prose with no tag at all and was never filtered. Both are now excluded, along with `Caveat:` and `[Request interrupted` prefixes.
- This is not cosmetic. `user_turns` feeds `card_user_turns`, and the difference between them is `human_turns_after_card` — the autonomy meter, and the number the whole compounding claim is measured by. On three engineers' real sessions, the injected text outnumbered what they actually typed, so the meter was reporting people as far more engaged with the card than they were. Measured numbers from before this fix should be treated as upper bounds.
- Loaded skill prose is still not caught. It carries no marker and is only detectable by its repetition across sessions, which a single transcript cannot see; the parser says nothing it cannot know.

## 0.16.0 — 2026-09-11
- **A rule is no longer created by a counter; it is proposed to a person.** Reaching `decisions.rule_threshold` now produces a *proposed* rule, and an authority accepts or rejects it with `gitvow rules accept|reject <n|finding|--all>`. Accepting creates precedent, which is itself a decision, so it is recorded the way decisions are: a `Gitvow-Rule-Accepted` or `Gitvow-Rule-Rejected` trailer on an empty commit, plus a note on `refs/notes/gitvow/rules` carrying the evidence the verdict was made against — the run, its dates, the people, the exceptions set aside. `gitvow show` prints it.
- **Re-run `gitvow install` in every repository after upgrading.** The `prepare-commit-msg` git hook body changed, because it now writes `Gitvow-Referred` and `to=`. Until it is rewritten, every existing install keeps the 0.15 hook: referrals recorded with `gitvow decide ... refer` never reach the commit, and the trailer a reader finds does not match the answer a person gave. `gitvow status` reports this as `git hooks written by an older gitvow` and names the file; it is a failure, not a warning, and it is per repository rather than per machine.
- The reason is not tidiness. Promotion by counting conflated four different kinds of decision — a universal best practice the model already knows, an organisation-wide standard that belongs at the organisation, a genuinely repository-specific call, and a situational one-off — and it made gitvow the author of binding policy that nobody had accepted, in a project whose whole claim is that authority is human and the machine never accepts its own consequence. Counting is gitvow's job. Deciding that a count means something is not. The danger was never too few rules: it is too many bad ones, which is the disease that kills a hand-maintained wiki arriving by another road.
- **A scoped answer can never earn a rule.** "Accepted, staging only" is an exception, not a precedent, and three of them are three exceptions rather than an agreement about the unconditional case. Scoped answers are set aside before the run is counted, so they neither reach the threshold nor break a run of plain answers, and each finding reports how many exceptions it has collected.
- A verdict by someone the policy does not name is refused rather than recorded and discounted. Their answers still count as evidence; a rule they wrote alone would be exactly the failure the mechanism exists to prevent.
- A rejection is neither a one-commit veto nor permanent: the proposal returns only after a full `rule_threshold` of answers dated *later* than the rejection, so an authority is shown fresh evidence rather than the evidence they already refused.
- Proposals are handed to the agent at session start and named on the card, in their own labelled section which says that nobody has accepted them, that they permit nothing and that they change nothing about what must be put to a person. Nothing that used to be visible went quiet; it stopped reading as policy.
- Upgrading: rules earned by the old counter arrive as proposals with their evidence intact and still reach the agent, labelled. `gitvow rules accept --all` adopts every one of them in a single commit, so the rules a repository runs on afterwards say who accepted them.
- **`gitvow decide <n> refer [--to <person-or-team>]`**, a third answer to the card. `Gitvow-Open` had been carrying two unrelated facts: *nobody has decided*, which is debt, and *you asked the wrong person*, which is a routing failure. They need opposite remedies, so a referral is now its own trailer (`Gitvow-Referred: <finding> by <person>[ to=<who>][: <reason>]`) and its own state, counted and listed apart from open debt in the digest and the pull request report. It closes the card and lets the commit through, because holding a commit against the wrong person produces a wrong answer rather than a right one, and it never counts towards a proposed rule.
- Session note schema 6: `decisions[]` gains `to`. Additive, as ever — an older note reads exactly as it did. The trailer grammar grew only by name: `Gitvow-Referred` and the two `Gitvow-Rule-*` trailers are new names an older gitvow does not match at all, `to=` rides on the new name rather than on `Gitvow-Accepted`, and no existing trailer changed its meaning or its token set.
- The card derives rules once per card rather than twice per finding, which a card with several findings used to pay for over and over.
- **`gitvow coverage` corroborates each session claim against the note behind it.** A `Gitvow-Session` trailer is a line anyone can type, and a hand-written one used to *raise* the number meant to detect a missing record. Each claim is now checked against the note the hook would have written, and claims with nothing behind them are counted and listed separately. It is not proof — a forger can write a note too, and the output says so — but it raises the floor from "type one line" to "understand the note refs", and it needs no keys. A repository with no note refs fetched (a shallow CI clone) is reported as *uncorroborated* rather than as a pile of findings, because reporting every commit there would be a claim about the repository rather than about the record. `--json` gains `commits`, `notes_available`, `verified`, `unverified`, `unverified_list` and `verified_coverage`; the window's total non-merge commit count is shown so the unknown class has a visible bound. Signing the decisions themselves is 0.17.
- **Fixed: a command finding could never converge, so it could never reach a threshold.** The subject of a command finding was the whole command line, which made `kubectl apply -f a.yaml` and `kubectl apply -f b.yaml` two different findings for ever: the person was asked afresh on every invocation with no record behind the question, and no command could reach `rule_threshold` even in a repository that ran it daily. The arguments are precisely the part that changes per run. A command finding is now identified by the program and the rule that stopped it — `run kubectl (cluster mutation)` — with the full command line carried as evidence, so the card still shows exactly what was going to run. Two rules matching the same program stay two findings, so a precedent set for one consequence cannot answer the other. Command decisions already in history parse exactly as they did and are untouched; they keep their own per-command-line groups and will not group with new ones, which costs nothing, because they never grouped with anything.
- **Fixed a false claim in the reference documentation.** `docs/reference/note.md` said the trailer grammar "only ever grows". It grows safely by new trailer *names* — an older gitvow does not match a name it has never heard of, which is why `Gitvow-Referred` and its `to=` were safe to add together — but never by a new tail token on a trailer that has already shipped. The finding is matched lazily and every suffix is optional, so an older parser meeting a token it does not know backtracks it *into* the finding: `Gitvow-Accepted: edit foo.go class=k7 by nikhil` reads on 0.15 as a decision about `edit foo.go class=k7`, silently forking the identity of every decision carrying it with no error anywhere. The docs and the code now say so, and a test pins it, because it constrains every future addition to the grammar.
